## CONOPS.txt
## ============================================================================
## K6Bus CONOPS
## Concept of Operations para generacion de proyectos, librerias y APIs externas
## ============================================================================

Estado: borrador inicial ampliado y actualizado
Fecha de actualizacion: 2026-08-08

Objetivo: definir la vision operativa de K6Bus y ProtobuZig como framework de
mensajeria tipada multi-lenguaje basado en ficheros .proto.

K6Bus no debe entenderse unicamente como una libreria, sino como un framework
capaz de generar proyectos completos de mensajeria tipada alrededor de un fichero
.proto.

## ============================================================================
## 1. Principio fundamental
## ============================================================================

La logica principal vive en Zig.

La serializacion, deserializacion, cifrado, codificacion, gestion de mensajes,
transportes, colas, PacketProcessor, Domain y demas elementos internos deben
existir en Zig.

Las APIs C, Vala, Go u otros lenguajes son fachadas o bindings generados sobre
la logica Zig.

No se debe duplicar en C, Vala o Go la logica central de K6Bus salvo que sea
estrictamente necesario.

Directriz:
- Zig implementa.
- C/Vala/Go exponen.
- No crear frameworks paralelos por lenguaje.

## ============================================================================
## 2. Objetivo de usuario
## ============================================================================

Un usuario parte de un fichero .proto propio con varios mensajes definidos.
El usuario quiere generar un proyecto utilizable en un lenguaje concreto.

El usuario no deberia tener que entender la estructura interna de K6Bus para
empezar a publicar o subscribirse a mensajes tipados.

El resultado deseado es que pueda generar un proyecto completo, compilarlo y
ejecutar ejemplos minimos desde el primer momento.

## ============================================================================
## 3. Herramienta de generacion
## ============================================================================

K6Bus debe proporcionar una herramienta de generacion de proyectos.
Nombre provisional:
- tools/genera

La herramienta no debe limitarse a generar ficheros sueltos.
Debe poder generar un proyecto completo, compilable y ejecutable.

## ============================================================================
## 4. Modos principales de uso
## ============================================================================

### 4.1. Proyecto autocontenido generado

Modo principal y recomendado para usuarios nuevos o proyectos cerrados.

El usuario obtiene un proyecto completo con:
- codigo generado a partir del .proto,
- runtime K6Bus necesario,
- build.zig,
- ejemplos minimos,
- headers/bindings si procede.

Este modo puede generar una libreria monolitica por proyecto.

### 4.2. Runtime K6Bus instalado o reutilizado

Modo avanzado futuro.
El usuario u organizacion instala K6Bus como runtime compartido y genera solo
codigo especifico de su .proto.

No es prioritario en la primera fase.

### 4.3. Modo minimo o tutorial

Modo simplificado para evaluacion rapida.
Puede implementarse despues del modo autocontenido principal.

## ============================================================================
## 5. Estructura conceptual de capas
## ============================================================================

Internamente K6Bus se compone de capas separadas:
- aplicacion,
- publishers/subscribers tipados,
- Domain,
- StreamQueueUP/DOWN,
- PacketProcessor,
- transportes,
- red.

Aunque internamente estas capas esten separadas, la distribucion final puede
empaquetarse como una unica libreria especifica del proyecto.

## ============================================================================
## 6. Libreria base frente a libreria especifica
## ============================================================================

Para el usuario final de C, Vala o Go se prefiere una libreria monolitica de
proyecto porque simplifica el uso.

Internamente puede seguir existiendo separacion conceptual entre K6Bus core,
codigo generado y API externa.

Para usuarios avanzados podra existir en el futuro un modo separado basado en
runtime compartido, pero no sera el flujo inicial recomendado.

## ============================================================================
## 7. Modo Zig
## ============================================================================

El usuario Zig usara directamente la API Zig generada.
En modo Zig tiene sentido generar wrappers de alto nivel como:
- EstacionPublisher
- EstacionSubscriber

Objetivo del modo Zig:
- Ergonomia.
- Codigo idiomatico Zig.
- Uso directo de tipos generados.
- Mantener ownership claro.

## ============================================================================
## 8. Modo C
## ============================================================================

El usuario C debe trabajar contra una API opaca.
La API C no debe exponer estructuras internas de Zig como Domain, QueueMgr,
PacketProcessor o Msg.

Debe exponer tipos opacos o estructuras C estables.

Regla:
- La API C tipada debe reutilizar la logica Zig generada cuando sea posible.
- No debe reimplementar en C lo que ya funciona en Zig.

## ============================================================================
## 9. Modo Vala
## ============================================================================

Vala debe apoyarse en la API C generada.
No se debe intentar que Vala conozca directamente estructuras internas Zig.
Vala consume la ABI C.

## ============================================================================
## 10. Modo Go
## ============================================================================

Go probablemente usara cgo sobre la API C.
No es prioridad inicial, pero el diseno de la API C debe ser limpio para
permitir esta capa en el futuro.

## ============================================================================
## 11. API C base
## ============================================================================

La API C base pertenece a K6Bus core.
Debe existir aunque no haya tipos generados de usuario.

Debe permitir como minimo:
- crear/cerrar Domain,
- enviar mensajes raw,
- enviar mensajes tipados genericos,
- subscribirse a mensajes.

## ============================================================================
## 12. API C tipada generada
## ============================================================================

Por cada mensaje del .proto de usuario se generara una API especifica.

Ejemplo conceptual:
- estacion_publish(...)
- estacion_subscribe(...)

Internamente, estas funciones deben serializar/deserializar usando codigo Zig y
llamar al runtime K6Bus, no reimplementar logica en C.

## ============================================================================
## 13. Reutilizacion de codigo Zig
## ============================================================================

Directriz esencial:
- No generar un framework paralelo en C.
- La API C actua como frontera ABI.
- La generacion de wrappers C puede ser compleja si eso permite mantener una sola
  implementacion real en Zig.

## ============================================================================
## 14. EstacionPublisher / EstacionSubscriber
## ============================================================================

Son wrappers Zig de ergonomia para proyectos Zig.
Pueden seguir existiendo y se usaran en modo Zig.
Para C, Vala o Go se generaran wrappers especificos de ABI.

No es obligatorio que la API C use directamente estos wrappers si eso complica
la frontera ABI.

## ============================================================================
## 15. Directorios de salida
## ============================================================================

Convencion general:
- generated/ para codigo generado.
- examples/ para ejemplos minimos.
- zig-out/ para artefactos de build.

Un proyecto generado debe poder compilar aunque el usuario no tenga instalado el
repositorio completo de ProtobuZig.

## ============================================================================
## 16. build.zig
## ============================================================================

Cada proyecto generado debe tener un build.zig util.
Debe permitir compilar libreria, ejemplos y bindings segun modo.

El build generado debe ser legible y no excesivamente magico.

## ============================================================================
## 17. Proyectos generados
## ============================================================================

El generador debe crear proyectos autocontenidos cuando sea posible.

Salidas futuras esperadas:
- Proyecto Zig completo.
- Proyecto C completo con lib estatica/header/ejemplos.
- Proyecto Vala apoyado en C ABI.

## ============================================================================
## 18. encdec.zig
## ============================================================================

Actualmente los ficheros generados por ProtobuZig esperan encontrar encdec.zig
en su mismo nivel.

Esta duplicacion es aceptable de momento.
Queda pendiente estudiar una solucion mas limpia.

El uso de enlaces simbolicos puede ser util en desarrollo, pero no debe ser
obligatorio para el usuario final.

## ============================================================================
## 19. Filosofia de distribucion
## ============================================================================

Para usuarios finales se prefiere:
- Proyecto autocontenido.
- Libreria monolitica especifica del proyecto cuando simplifique.
- Ejemplos minimos incluidos.
- Build claro.

## ============================================================================
## 20. Nombres
## ============================================================================

Se usara prefijo k6b_ para funciones base de K6Bus.
Se usara prefijo del mensaje en minusculas para funciones tipadas generadas.

## ============================================================================
## 21. Manejo de errores
## ============================================================================

La API C no debe exponer errores Zig directamente.
Debe usar codigos de resultado estables.

Las funciones que crean objetos pueden devolver NULL.
Las funciones operativas deben devolver K6B_Result.

## ============================================================================
## 22. Callbacks C
## ============================================================================

Los subscribers C se basaran en callbacks C.
El wrapper Zig debe garantizar que el objeto pasado al callback vive durante la
llamada.

Si el usuario quiere conservarlo, debe copiarlo.
Esta regla debe documentarse en el header.

## ============================================================================
## 23. Ownership en API C
## ============================================================================

No mezclar allocators del usuario C con allocators internos Zig salvo que se
defina una API explicita para ello.

La frontera ABI debe documentar claramente quien crea, quien posee y quien libera.

## ============================================================================
## 24. Compatibilidad multiplataforma
## ============================================================================

Objetivo inicial:
- Linux.

Objetivos posteriores:
- Windows.
- BSD.
- Otros entornos donde Zig sea viable.

No bloquear la arquitectura por plataformas futuras, pero tampoco complicar la
fase inicial por ellas.

## ============================================================================
## 25. Relacion con transportes
## ============================================================================

Los transportes pertenecen al core de K6Bus.
El usuario C normalmente no deberia crear transportes manualmente en la primera
version.

La configuracion de transportes vendra de Config.proto y ficheros de
configuracion.

## ============================================================================
## 26. Relacion con configuracion
## ============================================================================

Domain debe seguir entendiendo los ficheros de configuracion K6Bus.
Config.proto es la fuente formal de configuracion.

Avance reciente:
- TransportConfig ya puede modelar variantes de transporte mediante oneof params.
- ProtobuZig ya reconoce el oneof en parser/AST.
- Esto desbloquea un modelo mas limpio para MCast/Bcast/UDPStar/UnixSocketStar/Custom.

## ============================================================================
## 27. Fases de implementacion
## ============================================================================

Fase 0:
- Consolidar arquitectura interna actual.
- ifcTransport.
- ifcSubscriber.
- PacketProcessor.
- QueueMgr.
- MCastTransport funcional.

Fase 1:
- API C base minima: k6b_domain_create, k6b_domain_close, k6b_domain_send_raw.

Fase 2:
- API C base ampliada: k6b_domain_send_msg, k6b_domain_subscribe_msg,
  k6b_subscriber_close.

Fase 3:
- API C tipada para demo1.

Fase 4:
- tools/genera -use_zig: proyecto Zig completo desde .proto.

Fase 5:
- tools/genera -use_c: proyecto C completo desde .proto.

Fase 6:
- tools/genera -use_vala.

Fase 7:
- Runtime K6Bus instalado/reutilizable.

Fase 8:
- Go u otros lenguajes.

## ============================================================================
## 28. Riesgos
## ============================================================================

Riesgo: Duplicar logica en C, Vala o Go.
Mitigacion: Mantener la logica real en Zig y generar solo fachadas.

Riesgo: API C demasiado cercana a estructuras internas Zig.
Mitigacion: Usar tipos opacos y funciones wrapper.

Riesgo: Generador demasiado complejo demasiado pronto.
Mitigacion: Implementar por fases.

Riesgo: Encdec duplicado o rutas fragiles.
Mitigacion: Mantener copia local en generated por ahora y resolver despues.

Riesgo: Soporte oneof incompleto.
Mitigacion: Validar parser/AST, generacion union(enum), initDefault()/deinit(),
serializacion/deserializacion y mensajes internos de forma incremental.

## ============================================================================
## 29. Directrices de diseno
## ============================================================================

- Usar el diseno mas sencillo posible.
- No generalizar antes de tener una prueba real.
- No reimplementar en C lo que ya existe en Zig.
- Las APIs externas son fachadas.
- Los tipos internos de K6Bus no se exponen directamente a C.
- El usuario final debe poder compilar y ejecutar un proyecto generado sin
  conocer la arquitectura interna de K6Bus.
- Los proyectos generados deben incluir ejemplos minimos.
- El build generado debe ser util desde el primer momento.
- La libreria monolitica por proyecto es aceptable y deseable para simplificar.
- La arquitectura interna debe seguir separando core, codigo generado y API
  externa, aunque el artefacto final sea unico.
- Un proyecto generado debe ser legible.
- La opcion avanzada de runtime compartido no debe complicar la experiencia inicial.

## ============================================================================
## 30. Estado actual relacionado
## ============================================================================

A fecha de esta actualizacion:
- K6Bus tiene vertical end-to-end validado con LoopTransport.
- Shutdown rapido esta implementado y necesita validacion exhaustiva.
- ProtobuZig parsea Config.proto con oneof params.
- Falta generar Zig para oneof como union(enum).
- Falta completar soporte recursivo en message_internal_parser.

## ============================================================================
## 31. Conclusion
## ============================================================================

La vision operativa de K6Bus es generar proyectos completos y utilizables a
partir de ficheros .proto.

El core de K6Bus permanece en Zig.
La generacion para C, Vala, Go u otros lenguajes se construye como fachada sobre
la logica Zig.

El modo principal sera generar proyectos autocontenidos.

El avance reciente en oneof acerca Config.proto a un modelo de configuracion mas
limpio para transportes.
