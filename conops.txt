K6BUS / PROTOBUZIG - CONCEPT OF OPERATIONS
Actualizado: 2026-08-24

PROPOSITO DE ESTE DOCUMENTO
Este fichero describe como se espera generar, configurar, desplegar, utilizar y
cerrar el ecosistema K6Bus/ProtobuZig. No contiene el backlog detallado ni bugs
concretos de implementacion.

===============================================================================
1. VISION OPERATIVA
===============================================================================

K6Bus debe entenderse como un framework capaz de producir y ejecutar proyectos
de mensajeria tipada a partir de contratos .proto.

El modo principal de operacion es:

    contrato .proto
        -> generacion Zig
        -> proyecto K6Bus tipado
        -> configuracion de topologia
        -> ejecucion distribuida

La implementacion principal vive en Zig. Las interfaces para C, Vala, Go u
otros lenguajes exponen la funcionalidad Zig sin duplicar su logica.

===============================================================================
2. ACTORES Y RESPONSABILIDADES
===============================================================================

Desarrollador de mensajes:
- define mensajes y enums en ficheros .proto;
- utiliza ProtobuZig para generar tipos y APIs;
- utiliza la API Zig segura para construir y consultar mensajes.

Desarrollador de aplicacion:
- define publishers, subscribers, callbacks y logica de negocio;
- no necesita conocer los transportes fisicos concretos;
- publica y recibe mensajes tipados.

Integrador/desplegador:
- define dominios, transportes, topologia, formatos, batching y arranque mediante
  configuracion;
- puede cambiar la infraestructura sin recompilar la logica de negocio cuando
  el contrato lo permita.

ProtobuZig:
- parsea .proto;
- construye el AST;
- genera raw/impl Zig;
- genera la API Zig segura;
- genera funciones de ownership y formatos.

K6Bus Runtime:
- crea dominios, colas, threads, publishers, subscribers y transportes;
- enruta mensajes localmente y entre nodos;
- aplica las politicas runtime configuradas.

===============================================================================
3. FLUJO DE GENERACION
===============================================================================

Flujo recomendado:

    uno o varios .proto
          |
          v
      ProtobuZig
          |
          +--> raw/impl Zig
          +--> *_api.zig
          +--> soporte de serializacion y texto
          |
          v
    generadores adicionales
          |
          +--> wrappers pub/sub tipados
          +--> soporte de seguridad/configuracion
          +--> futura C ABI y headers
          |
          v
   proyecto K6Bus autocontenido

Los generadores de pub/sub y seguridad pueden trabajar sobre el Zig generado
por ProtobuZig cuando esto mantenga una separacion mas sencilla y evite acoplar
cada generador al AST interno.

===============================================================================
4. MODOS DE DISTRIBUCION
===============================================================================

4.1. Proyecto autocontenido generado

Es el modo principal inicial. Incluye:
- codigo raw/impl generado;
- API Zig segura;
- runtime K6Bus necesario;
- build.zig;
- configuraciones y ejemplos;
- headers o bindings cuando proceda.

4.2. Runtime K6Bus instalado y reutilizable

Modo futuro para organizaciones que quieran compartir una version estable del
runtime entre varios proyectos.

4.3. Modo minimo/tutorial

Distribucion reducida para evaluacion, aprendizaje y pruebas rapidas. Se aborda
despues de estabilizar el modo autocontenido.

===============================================================================
5. ARRANQUE DE UN DOMAIN
===============================================================================

Secuencia operativa:

    fichero/configuracion
          |
          v
    parseo de AppConfig
          |
          v
    Domain.create/createEx
          |
          +--> seleccion de DomainConfig
          +--> extraccion de runtime config
          +--> creacion de transportes
          +--> creacion de crossconnectors
          +--> configuracion de batching y arranque
          |
          v
    duplicacion de valores que deban persistir
          |
          v
    liberacion de AppConfig temporal
          |
          v
    Domain operativo

Domain conserva solamente los valores runtime necesarios. Los objetos creados
durante init copian cualquier string o slice que necesiten despues del arranque.

===============================================================================
6. OPERACION PUBLISH/SUBSCRIBE
===============================================================================

Publicacion:

    aplicacion
       -> Publisher tipado
       -> Domain.sendMsg()
       -> StreamQueueDOWN
       -> entrega local y/o transportes

Recepcion:

    transporte
       -> PacketProcessor
       -> StreamQueueUP
       -> filtro de canal y tipo
       -> cola propia del Subscriber
       -> hilo/callback de aplicacion

El codigo de usuario no se ejecuta en los hilos que reciben paquetes ni bajo
locks de infraestructura.

La entrega puede funcionar en modo inmediato o batch segun la configuracion del
Domain. Publishers y subscribers no necesitan conocer esa politica.

===============================================================================
7. TOPOLOGIA Y TRANSPORTES
===============================================================================

La topologia se define mediante configuracion. Una aplicacion puede utilizar
entrega local y uno o varios transportes sin cambiar la logica de los mensajes.

Transportes previstos incluyen multicast, broadcast, UDP star, Unix socket
star y adaptadores futuros para otros sistemas de mensajeria.

El transporte fisico mueve bytes. La serializacion, el cifrado, el routing y la
logica de negocio pertenecen a capas separadas.

Los crossconnectors permiten conectar transportes dentro de una instancia y
deben evitar bucles de reenvio y mensajes propios.

===============================================================================
8. USO DE LA API ZIG SEGURA
===============================================================================

La aplicacion utiliza preferentemente los wrappers *_api.zig en lugar de
manipular directamente el raw generado.

Flujo tipico:

    var msg = try Tipo.initDefault(allocator);
    defer msg.deinit(allocator);

    try msg.setCampo(...);
    try publisher.publish(msg);

La API segura distingue vistas borrowed y copias owned. Las operaciones con
messages realizan copia profunda cuando el contrato lo requiere. Los cambios de
rama oneof liberan de forma segura la rama anterior.

El raw/impl permanece como capa interna para datos, formatos y compatibilidad
con el codigo generado.

===============================================================================
9. FORMATOS
===============================================================================

ProtobuZig proporciona un modelo comun de mensajes con varias representaciones:
- binario Protocol Buffers;
- representaciones binarias auxiliares como Base64;
- Protobuf Text;
- ZON y JSON segun el alcance soportado.

Los formatos propios que parten de initDefault() conservan defaults definidos
por el contrato. ZON y JSON se tratan como configuraciones explicitas: todos los
required deben estar presentes y no se crean defaults owned implicitos despues
del parseo.

===============================================================================
10. CIERRE
===============================================================================

Cierre rapido:
- Domain marca running=false al comienzo;
- despierta y detiene la infraestructura;
- puede descartar mensajes pendientes;
- libera correctamente cualquier mensaje descartado;
- no garantiza entrega completa;
- no bloquea indefinidamente.

Cierre graceful futuro:
- intenta drenar colas dentro de un timeout;
- informa si el timeout impide completar la entrega;
- mantiene las mismas garantias de ausencia de leaks y double-free.

===============================================================================
11. OTROS LENGUAJES
===============================================================================

La futura API C presenta handles opacos y funciones explicitas de creacion,
consulta, publicacion, cierre y destruccion.

Vala utiliza esa C ABI. Go puede utilizarla mediante cgo. Ninguna fachada
reimplementa serializacion, ownership o routing si puede delegarlos en Zig.

===============================================================================
12. ESCENARIO DE REFERENCIA
===============================================================================

1. Un equipo define mensajes de control y telemetria en .proto.
2. ProtobuZig genera raw/impl y API segura.
3. Un generador crea wrappers pub/sub tipados sobre el Zig generado.
4. La aplicacion implementa callbacks y logica en Zig.
5. El integrador configura dominios, multicast y entrega local.
6. Domain crea la infraestructura y libera la configuracion temporal.
7. Publishers envian mensajes sin conocer el transporte.
8. Subscribers reciben en hilos desacoplados.
9. El mismo nucleo puede exponerse despues mediante C, Vala o Go.
10. El cierre libera colas, mensajes, transportes y memoria owned.

===============================================================================
13. EVOLUCION PREVISTA
===============================================================================

La evolucion se realiza por capas:
1. consolidar codigo generado, formatos y ownership;
2. consolidar runtime y transportes principales;
3. generar proyectos autocontenidos completos;
4. añadir seguridad y generadores pub/sub;
5. definir una API C opaca;
6. añadir fachadas para otros lenguajes;
7. medir y optimizar sobre escenarios reales.
