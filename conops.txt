## K6Bus CONOPS
## Concept of Operations para K6Bus y ProtobuZig
## ============================================================================
Fecha de actualizacion: 2026-08-18
Estado: documento vivo actualizado tras consolidar API segura generada, accessors de message/oneof y fixes de serializacion binaria.

## ============================================================================
## 1. Vision operativa
## ============================================================================
K6Bus no debe entenderse solo como una libreria, sino como un framework capaz de generar proyectos completos de mensajeria tipada a partir de ficheros .proto.

La logica principal vive en Zig. Las APIs C, Vala, Go u otros lenguajes son fachadas o bindings sobre la logica Zig.

Directriz:
- Zig implementa.
- C/Vala/Go exponen.
- No crear frameworks paralelos por lenguaje.
- La API Zig segura generada por ProtobuZig es la capa recomendada para construccion ergonomica y segura de mensajes.

## ============================================================================
## 2. Relacion K6Bus/ProtobuZig
## ============================================================================
K6Bus y ProtobuZig evolucionan como proyectos independientes pero complementarios.

ProtobuZig:
- parsea .proto,
- genera AST,
- genera tipos Zig raw/impl,
- genera API segura *_api.zig,
- genera initDefault()/deinit(),
- genera serializacion/deserializacion,
- genera soporte multi-formato.

K6Bus:
- usa esos tipos generados,
- define runtime Pub/Sub,
- crea dominios, transportes, colas y subscribers,
- usa Config.proto como contrato formal de configuracion,
- guarda tambien los *_api.zig generados en src/generated cuando la API segura forma parte del flujo de desarrollo.

mecha:
- no es parte del proyecto K6Bus/ProtobuZig,
- es una dependencia externa usada por ProtobuZig como parser combinator.

## ============================================================================
## 3. Configuracion como entrada de arranque
## ============================================================================
Decision consolidada:
- AppConfig y DomainConfig completos son configuracion temporal de arranque.
- Domain no conserva todo el arbol de configuracion parseado.
- Domain extrae y conserva solo configuracion runtime minima.
- Tras init, app_cfg.deinit(allocator) libera la memoria parseada desde ZON.

Valores runtime persistentes en Domain:
- binary_format,
- dispatch_mode,
- dispatch_batch_time_ms,
- start_at_init.

Durante init se usa DomainConfig completo para:
- crear transportes,
- crear crossconnectors,
- aplicar politica inicial de batching,
- definir arranque.

Condicion critica:
- Los objetos creados a partir de configuracion deben copiar strings/slices que vayan a conservar.

Semantica de defaults en config generada:
- optional con default explicito se materializa en initDefault().
- optional sin default queda null.
- durante deserializacion se parte de initDefault() y se aplican campos recibidos.

## ============================================================================
## 5. Capas conceptuales
## ============================================================================
Internamente K6Bus contiene:
- aplicacion,
- publishers/subscribers tipados,
- Domain,
- StreamQueueUP/DOWN,
- QueueMgr,
- PacketProcessor,
- transportes,
- red.

La distribucion final puede empaquetarse como una libreria especifica del proyecto, aunque internamente haya separacion clara.

En ProtobuZig, la separacion recomendada es:
- raw/impl generado: datos, initDefault/deinit y formatos.
- *_api.zig: wrappers seguros, clone, setters/getters/builders y control de ownership.
- C ABI futura: fachada opaca sobre la API Zig segura, no sobre el raw.

## ============================================================================
## 6. Config.proto y oneof
## ============================================================================
Config.proto es la fuente formal de configuracion de K6Bus.

Avance consolidado:
- TransportConfig usa oneof params.
- ProtobuZig parsea y representa oneof en AST.
- ProtobuZig genera union(enum) para oneof con alternativa none: void.
- La configuracion ZON usa union(enum):
  .params = .{ .mcast = .{ ... } }
  .params = .{ .bcast = .{ ... } }
  .params = .{ .udpstar = .{ ... } }
  .params = .{ .usoxstar = .{ ... } }
- Demo1 carga ZON con oneof y finaliza sin leaks.
- La API segura generada ya cubre oneof message/scalar/enum/string/bytes.

Pendiente en raw/formats:
- Protobuf Text para oneof.
- JSON para oneof.
- escritura/lectura ZON round-trip completa con union(enum).

## ============================================================================
## 7. API segura generada
## ============================================================================
ProtobuZig genera wrappers *_api.zig encima del raw/impl.

Cada wrapper publico tiene forma:
- struct { impl: TipoImpl }

Capacidades consolidadas:
- initDefault()
- deinit()
- clone()
- serializeToBin()/deserializeFromBin()
- writeToText()/readFromText()
- writeToFile()/readFromFile()
- required/optional/repeated scalar y enum
- required/optional/repeated string y bytes
- required/optional/repeated message
- oneof message/scalar/enum/string/bytes

Reglas operativas:
- cloneImpl(comptime T) usa seriigiAlBin(.BF_PROTOBUF) + deseriigiElBin(.BF_PROTOBUF).
- get de string/bytes devuelve vista borrowed.
- get de message devuelve copia owned y requiere deinit() por el usuario.
- append/set de message copia profundamente.
- oneof set clona/duplica antes de borrar la rama anterior.
- oneof clear libera la rama activa segun tipo y deja .none.

## ============================================================================
## 8. API C y otros lenguajes
## ============================================================================
El usuario C debe trabajar contra una API opaca.

La API C no debe exponer estructuras internas como Domain, QueueMgr, PacketProcessor o Msg.

Vala se apoyara en C ABI. Go probablemente usara cgo sobre API C.

Directriz:
- No duplicar logica en C/Vala/Go.
- Mantener logica real en Zig.
- Empezar probablemente por una API C manual de K6Bus runtime.
- Para mensajes, la futura C ABI debe delegar en la API Zig segura y no duplicar reglas de ownership.
- Evitar parsear *_api.zig si se puede reutilizar el AST o un modelo intermedio.

## ============================================================================
## 9. Ownership
## ============================================================================
Principio operativo:
- create/initDefault actuan como constructores.
- deinit actua como destructor.
- Todo objeto que posea memoria tiene ruta clara de liberacion.

Decision consolidada:
- AppConfig parseado desde ZON se libera al terminar createEx/init.
- Domain no se queda con slices prestados del AppConfig.
- Los transportes deben duplicar lo que conserven.
- El buffer temporal decoded de BF_BASE64 debe liberarse tras deserializar.
- Repeated debe preservar orden tras round-trip binario.

## ============================================================================
## 10. Riesgos actuales
## ============================================================================
Riesgo: transportes con strings prestados desde configuracion temporal.
Mitigacion: revisar createEx/create de transportes y duplicar strings conservados.

Riesgo: defaults string/bytes como literales en campos owned.
Mitigacion futura: centralizar defaults owned en initDefault().

Riesgo: dos enums similares pero nominalmente distintos.
Mitigacion: helper explicito BinaryFormat -> BinaraFormato por valor.

Riesgo: soporte incompleto de oneof en formatos de texto raw.
Mitigacion: implementar Protobuf Text primero; validar ZON/JSON despues.

Riesgo: directorios generated duplicados durante pruebas.
Mitigacion: usar siempre output_dir previsto y borrar generados temporales.
