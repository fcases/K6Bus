generados (optional/repeated) para que ZON/JSON acepten campos ausentes.

Contexto (verificado el 2026-08-30):
- std.zon.parse (zon/parse.zig:794-805) y std.json (fillDefaultStructValues en
  static.zig) solo rellenan campos ausentes si la declaracion Zig del campo
  tiene default; si no, error (ParseZon / MissingField).
- Con el Config.zig actual: {"id":77} sin cross_connectors -> MissingField;
  .{ .id = 77 } -> ParseZon. El dolor NO es del esquema repeated, es de los
  parsers: cualquier optional/repeated omitido rompe el parseo.
- Decision de diseno: MANTENER cross_connectors como repeated (multi-grupo es
  util para topologias segmentadas SCADA; un grupo = lista de 1 elemento; el
  optional de C#/Vala era una simplificacion, no una capacidad).

Solucion propuesta (en el generador, no en el esquema): emitir defaults de
declaracion en los campos:
  - optional sin default proto  ->  ?T = null
  - repeated                    ->  []T = &.{}
Con esto ambos parsers rellenan automaticamente los campos ausentes y un
domain sin crossconnectors se escribe omitiendo el campo (y el cfg raiz deja
de necesitar la linea .cross_connectors = .{}).

Validado empiricamente con GPA: ZON rellena los missing con los defaults
(nombre.len=0, cross.len=0, opt=null) y el free de slices vacias no pierde ni
crashea.

ADVERTENCIA: NO poner defaults estaticos en optional-con-default OWNED
(p. ej. local_address = "Any" como default de declaracion): si el campo queda
en el default de declaracion, deinit() liberaria un literal estatico (invalid
free). Para esos campos el default debe ser = null. Esto es coherente con
Directrices seccion 10 (ZON/JSON no materializan defaults owned implicitos
tras el parseo). initDefault() sigue materializando los defaults del proto.

Pendiente de estudio: si el optional CON default proto debe quedar en null o
en el default cuando el campo se omite en ZON/JSON (hoy no se puede omitir);
coherencia con la semantica proto2 (campo ausente = default).
