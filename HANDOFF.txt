## ============================================================================
## 3. Arquitectura actual de K6Bus
## ============================================================================
K6Bus es un middleware Pub/Sub en Zig orientado a sistemas, robotica, automatizacion, SCADA y aplicaciones de tiempo real.

Piezas principales:
- Domain es el nucleo local del bus.
- No hay singleton global.
- Puede haber multiples Domain en un mismo proceso.
- Domain se crea en heap y se referencia mediante puntero estable.
- Publishers publican mediante Domain.
- Subscribers reciben de forma desacoplada mediante cola e hilo propios.
- StreamQueueDOWN distribuye hacia transportes y entrega local.
- StreamQueueUP distribuye hacia subscribers.
- QueueMgr gestiona colas, threads, condiciones, batching y dispatch.
- Los transportes concretos son objetos reales que mueven bytes.
- PacketProcessor no debe ser confundido con transporte.

## ============================================================================
## 4. Configuracion y ownership
## ============================================================================
Decision cerrada:
- AppConfig y DomainConfig completos son configuracion temporal de arranque.
- Domain no conserva el arbol completo de configuracion tras init.
- Domain conserva solo una configuracion runtime pequena con valores baratos:
  - binary_format
  - dispatch_mode
  - dispatch_batch_time_ms
  - start_at_init
  - direct_dispatch_to_subs
- LoadTransports(dom_cfg) y CreateCrossConnections(dom_cfg) reciben DomainConfig temporal durante init.
- app_cfg.deinit(allocator) se ejecuta despues de init, liberando memoria parseada.

Condicion importante:
- Todo transporte o componente creado desde configuracion debe copiar cualquier string/slice que vaya a conservar despues de createEx()/createFromFile().
- Si solo usa strings durante creacion, no necesita copiarlos.

## ============================================================================
## 6. BinaraFormato vs BinaryFormat
## ============================================================================
Estado actual:
- ProtobuZig genera BinaraFormato.
- Config.proto define BinaryFormat.
- Ambos enums tienen valores alineados en la parte comun.

BinaraFormato actual esperado:
- BF_PROTOBUF = 0
- BF_OMG_CDR = 1
- BF_ASN1_BER = 2
- BF_ASN1_DER = 3
- BF_BASE64 = 10
- BF_BINPB2TEKSTO_HEX = 11
- BF_BINPB2TEKSTO_DEC = 12

BinaryFormat en Config.proto:
- BF_PROTOBUF = 0
- BF_OMG_CDR = 1
- BF_ASN1_BER = 2
- BF_ASN1_DER = 3

Nota:
- Aunque ambos sean enum(u64), Zig los trata como tipos distintos.
- Se recomienda conversion explicita por valor:

pub fn binaryFormatToBinaraFormato(v: BinaryFormat) BinaraFormato {
    return std.meta.intToEnum(BinaraFormato, @intFromEnum(v)) catch .BF_PROTOBUF;
}

## ============================================================================
## 7. ProtobuZig ownership/leaks
## ============================================================================
Estado cerrado por ahora:
- initDefault()/deinit() se mantiene como mecanismo simetrico.
- required enum sin default explicito inicializa al valor 0.
- optional enum sin default queda null.
- repeated enum inicializa slice vacio.
- deseriigi() binario genera errdefer de limpieza.
- deseriigi() binario usa temporales para required string/bytes.
- deseriigi() binario usa temporales para optional string/bytes.
- deseriigi() binario usa temporales para repeated scalar/string/bytes/message antes de liberar valores anteriores.
- oneof construye nueva rama antes de deinitDatos().
- legiElProtobufTeksto() genera errdefer tras initDefault().
- No quedan leaks conocidos pendientes tras demo2.

Pendiente posible:
- Revisar JSON/ZON si tienen parsers propios con initDefault() + overwrite.
- Anadir tests especificos de error-path.

## 10. Fase wrappers API propuesta
## ============================================================================
Fase actual:
- cctrol.zig contiene tipos raw actuales.

Fase intermedia propuesta:
- cctrol.zig mantiene tipos raw actuales.
- cctrol_api.zig genera wrappers seguros, por ejemplo EstMeteo/EstRemCtrol API o EstMeteoApi/EstRemCtrolApi segun decision de nombres.
- append de repeated message hace copia profunda.
- getXAt(index) devuelve copia owned y el usuario debe llamar deinit().
- serializeToBin/deserializeFromBin y writeToText/readFromText son API publica en ingles.

Fase final posible:
- cctrol_impl.zig contiene EstMeteo_impl, EstRemCtrol_impl, etc.
- cctrol.zig contiene wrappers publicos EstMeteo, EstRemCtrol, etc.
- k6b-genpubsub podria generar contra wrappers publicos.
- APIs C/Vala/Go se apoyarian en wrappers/handles.

Ejemplo de API objetivo:

var meteo = try EstMeteo.initDefault(allocator);
defer meteo.deinit(allocator);
try meteo.setNombre(allocator, "meteo-remota-1");
meteo.setTemp(23);
meteo.setVViento(12.5);

var remota = try EstRemCtrol.initDefault(allocator);
defer remota.deinit(allocator);
try remota.setNombre(allocator, "remota-1");
try remota.appendMeteo(allocator, &meteo);

var meteo2 = try remota.getMeteoAt(allocator, 0);
defer meteo2.deinit(allocator);
