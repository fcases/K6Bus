K6BUS / PROTOBUZIG - RESUMEN DEL PROYECTO
Actualizado: 2026-08-24

PROPOSITO DE ESTE DOCUMENTO
Este fichero explica que son K6Bus y ProtobuZig, como se relacionan y cual es
su estado general. No contiene el backlog detallado ni el punto exacto de
continuacion de una sesion.

===============================================================================
1. VISION GENERAL
===============================================================================

K6Bus es un middleware de mensajeria distribuida Publish/Subscribe orientado a
sistemas, robotica, automatizacion, SCADA y aplicaciones de tiempo real.

Sus objetivos principales son:
- no depender de una maquina virtual;
- mantener compatibilidad C ABI;
- permitir multiples dominios y transportes;
- definir la topologia mediante configuracion;
- desacoplar productores, consumidores y transportes;
- priorizar robustez, simplicidad operacional y ownership explicito.

ProtobuZig es un compilador/generador Protocol Buffers independiente de K6Bus,
pero complementario. A partir de ficheros .proto genera tipos Zig, funciones de
inicializacion y liberacion, serializacion/deserializacion y una API Zig segura.

La logica real del ecosistema vive en Zig. Las futuras APIs C, Vala, Go u otros
lenguajes seran fachadas sobre la implementacion Zig, no implementaciones
paralelas.

===============================================================================
2. RELACION ENTRE K6BUS Y PROTOBUZIG
===============================================================================

Flujo previsto:

    ficheros .proto
          |
          v
      ProtobuZig
          |
          +--> tipos raw/impl Zig
          +--> API Zig segura *_api.zig
          +--> funciones de formatos y ownership
          |
          v
       K6Bus
          |
          +--> publishers/subscribers tipados
          +--> runtime de dominios, colas y transportes
          +--> futura C ABI y bindings

ProtobuZig no depende conceptualmente de K6Bus. K6Bus utiliza el codigo generado
por ProtobuZig para su configuracion y sus mensajes tipados.

mecha es una dependencia externa usada por ProtobuZig para parsing; no forma
parte de K6Bus ni de ProtobuZig.

===============================================================================
3. ARQUITECTURA GENERAL DE K6BUS
===============================================================================

Flujo descendente:

    Aplicacion
       -> Publisher
       -> Domain
       -> StreamQueueDOWN
       -> Transportes
       -> Red

Flujo ascendente:

    Red
       -> Transportes
       -> Domain
       -> StreamQueueUP
       -> Subscriber
       -> Aplicacion

Entrega local:

    StreamQueueDOWN -> StreamQueueUP

Piezas principales:
- Domain es el nucleo local del bus.
- No existe un singleton global; pueden coexistir varios Domain.
- Domain se crea en heap para mantener una direccion estable.
- QueueMgr gestiona colas, mutex, condiciones, threads, batching y dispatch.
- StreamQueueUP distribuye hacia subscribers.
- StreamQueueDOWN distribuye hacia transportes y entrega local.
- Cada subscriber dispone de cola e hilo propios.
- El codigo de usuario no se ejecuta en los hilos de infraestructura.
- Los transportes fisicos mueven bytes y no conocen tipos protobuf concretos.

La separacion ifcTransport + PacketProcessor + QueueMgr esta validada. El
transporte multicast funciona en Linux, incluyendo pruebas locales mediante
IP_MULTICAST_LOOP=1 y filtrado de paquetes propios mediante tx_port.

===============================================================================
4. CONFIGURACION Y CICLO DE VIDA
===============================================================================

Config.proto es el contrato formal de configuracion de K6Bus.

AppConfig y DomainConfig completos se utilizan como configuracion temporal de
arranque. Domain extrae solamente una configuracion runtime minima:
- binary_format;
- dispatch_mode;
- dispatch_batch_time_ms;
- start_at_init.

Durante la inicializacion, la configuracion completa se utiliza para crear
transportes, crossconnectors y topologia. Despues se libera. Cualquier objeto
que necesite conservar strings o slices de la configuracion debe copiarlos.

Domain se crea mediante create() o createEx(). createEx() permite overrides
puntuales de configuracion runtime.

===============================================================================
5. ESTADO GENERAL DE PROTOBUZIG
===============================================================================

Capacidades consolidadas:
- parser .proto orientado principalmente a proto2;
- AST propio;
- resolucion de tipos y referencias adelantadas en casos validados;
- generacion de tipos Zig raw/impl;
- initDefault() y deinit();
- serializacion y deserializacion binaria protobuf;
- soporte binario de oneof con semantica last-one-wins;
- representacion de oneof como union(enum) con alternativa interna none;
- generacion de API segura *_api.zig;
- soporte de required, optional y repeated para scalar, enum, string, bytes y
  message en la API segura;
- API segura para oneof message, scalar, enum, string y bytes;
- clonacion profunda inicial mediante round-trip binario;
- preservacion del orden de repeated en round-trip binario;
- soporte BF_BASE64 con liberacion del buffer temporal decoded.

Cctrol.proto se ha validado con referencias adelantadas, enum TipoPanel y oneof
datos con SenialInfo/TextoInfo.

===============================================================================
6. API ZIG SEGURA GENERADA
===============================================================================

Cada wrapper publico tiene la forma general:

    pub const Tipo = struct {
        impl: TipoImpl,
    };

La API proporciona construccion, liberacion, clonacion, IO y accessors seguros.

Semantica general:
- get de scalar o enum devuelve valor;
- get de string o bytes devuelve una vista borrowed;
- get de message devuelve una copia owned que el usuario debe liberar;
- set y append de message realizan copia profunda;
- los cambios de rama oneof liberan la rama owned anterior.

===============================================================================
7. PROTOBUF TEXT
===============================================================================

El parser de Protobuf Text utiliza ahora un CustomTokenizer generado, en lugar
de tokenizeAny. En los casos probados conserva cadenas entre comillas con
espacios y reconoce enteros, decimales, negativos y notacion cientifica.

Se ha validado:
- texto con espacios;
- comillas escapadas en las pruebas actuales;
- numeros flotantes y notacion cientifica;
- round-trip Protobuf Text de PanelBase.datos para ramas oneof TYPE_MESSAGE;
- optional string mediante la API segura.

El frente actual es completar repeated en Protobuf Text y asegurar que la
transferencia de ownership no introduce leaks, double-free ni copias
superficiales.

===============================================================================
8. ESTADO GENERAL DE K6BUS
===============================================================================

Se encuentran avanzados o validados:
- Domain/create/createEx;
- QueueMgr;
- StreamQueueUP y StreamQueueDOWN;
- publishers y subscribers tipados;
- LoopTransport;
- MCastTransport en Linux;
- configuracion ZON con oneof;
- shutdown rapido sin leaks en las pruebas consolidadas;
- uso de Config.proto generado por ProtobuZig;
- ejemplos de pub/sub y codificacion en demo2.

Los siguientes frentes generales son:
- completar la robustez de formatos y ownership en ProtobuZig;
- optimizar el filtrado por msgType antes de clonar y encolar;
- auditar strings/slices conservados por transportes;
- continuar transportes y crossconnectors;
- desarrollar generadores de claves y pub/sub sobre el Zig ya generado;
- preparar posteriormente la API C opaca.

===============================================================================
9. OBJETIVO FINAL
===============================================================================

El objetivo es disponer de un ecosistema compuesto por:
- ProtobuZig como compilador/generador Protocol Buffers;
- API Zig segura generada;
- K6Bus Runtime como middleware distribuido;
- generadores adicionales sobre el Zig generado;
- proyectos autocontenidos generados;
- compatibilidad C ABI;
- fachadas para Vala, Go y otros lenguajes;
- infraestructura configurable, multi-dominio y multi-transporte.
