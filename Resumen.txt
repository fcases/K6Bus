### =====================================================================
K6BUS - RESUMEN DEL PROYECTO
### =====================================================================

Actualizado: 2026-08-08

K6Bus es un middleware de mensajeria distribuida orientado a sistemas, robotica, automatizacion, SCADA y aplicaciones de tiempo real. Su objetivo es proporcionar una infraestructura Publish/Subscribe robusta, desacoplada y configurable, que permita intercambiar mensajes entre procesos y nodos distribuidos sin depender de maquinas virtuales y manteniendo compatibilidad C ABI.

K6Bus y ProtobuZig son proyectos independientes pero complementarios.

### =====================================================================
VISION
### =====================================================================

- Middleware sin maquina virtual.
- Compatible con C ABI.
- Escalable horizontalmente.
- Multi-dominio.
- Multi-transporte.
- Multi-lenguaje.
- Configurable mediante ficheros.
- Orientado a robustez y simplicidad operacional.

### =====================================================================
PRINCIPIOS RECTORES
### =====================================================================

- Las aplicaciones intercambian mensajes.
- La topologia de comunicaciones se define mediante configuracion.
- La infraestructura debe ser robusta, desacoplada y distribuible.
- La aplicacion define mensajes, publishers, subscribers y logica.
- La configuracion define transportes, topologias, batching, arranque, formatos y cifrado.
- No se comparten objetos de aplicacion entre nodos.
- Todo intercambio entre nodos se realiza mediante mensajes.

### =====================================================================
ARQUITECTURA K6BUS
### =====================================================================

DOWN:
Aplicacion -> Publishers -> Domain -> StreamQueueDOWN -> Transportes -> Red

UP:
Red -> Transportes -> StreamQueueUP -> Subscribers -> Aplicacion

Entrega local directa:
StreamQueueDOWN -> StreamQueueUP

La infraestructura utiliza colas y threads desacoplados para evitar bloqueos entre productores y consumidores.

### =====================================================================
DOMAIN
### =====================================================================

Domain es el nucleo local del bus.

Caracteristicas:
- No existe singleton global.
- Pueden coexistir multiples Domain en un proceso.
- Domain se crea en heap y se referencia mediante puntero estable.
- Domain se crea mediante create() o createEx().
- create() usa configuracion sin overrides.
- createEx() permite overrides puntuales de dispatch_mode y dispatch_batch_time_ms.

Decision reciente:
- Domain no conserva DomainConfig completo.
- Domain conserva una configuracion runtime minima:
  - binary_format
  - dispatch_mode
  - dispatch_batch_time_ms
  - start_at_init
- AppConfig/DomainConfig completos son temporales durante createEx/init.
- LoadTransports(dom_cfg) y CreateCrossConnections(dom_cfg) reciben DomainConfig temporal.
- app_cfg.deinit(allocator) libera la memoria parseada tras la inicializacion.

Estado validado:
- Demo1 carga configuracion ZON con oneof y cierra sin leaks.

### =====================================================================
CONFIGURACION
### =====================================================================

Config.proto constituye la definicion formal de la infraestructura.

Politica de carga:
- k6bus.App.zon.cfg
- k6bus.App.pb.cfg
- k6bus.App.json.cfg
- defaults de Config.proto

Avance reciente:
- TransportConfig usa oneof params.
- ZON de entrada funciona con union(enum), usando sintaxis .{ ... } y no &.{ ... }.
- El ejemplo correcto para params es:
  .params = .{ .mcast = .{ ... } }

### =====================================================================
PROTOBUZIG
### =====================================================================

ProtobuZig es una herramienta independiente de K6Bus.

Funciones principales:
- Parseo de .proto.
- Generacion de AST.
- Generacion de estructuras Zig.
- Generacion de initDefault().
- Generacion de deinit().
- Generacion de serializacion/deserializacion.
- Soporte multi-formato.

Estado actual:
- Proto2 como objetivo principal.
- Parser principal funcionando.
- AST propio.
- Generacion Zig.
- Binarizacion/desbinarizacion proto2 en progreso avanzado.
- Soporte inicial de oneof implementado.

Oneof ya realizado:
- Parser reconoce oneof.
- AST contiene OneOfDecl / OneOfField.
- Resolucion de tipos para OneOfField.
- Generacion union(enum) con none: void.
- Campo params: Params.
- initDefault() con .{ .none = {} }.
- deinitParams().
- deinit() llama al helper oneof.
- seriigi/deseriigi binarios para oneof.

Pendiente oneof:
- Protobuf Text.
- JSON.
- Validar escritura ZON con union(enum).
- oneof en mensajes internos en fase posterior.

### =====================================================================
OWNERSHIP
### =====================================================================

Pilar fundamental:
- Cada objeto tiene un propietario claro.
- create/initDefault construye.
- deinit destruye.
- shutdown no debe producir leaks ni double-free.

Estado reciente:
- Leak del buffer temporal de legiTiponElDosiero corregido con defer allocator.free(enhavo).
- Leaks de std.zon.parse resueltos liberando AppConfig tras init.
- Demo1 sin leaks tras cierre.

Pendiente:
- Revisar transportes para asegurar que no conservan slices prestados de AppConfig temporal.
- Revisar defaults string/bytes generados como literales.

### =====================================================================
TRANSPORTES
### =====================================================================

Transportes previstos:
- MCAST.
- BCAST.
- UDPSTAR.
- USOXSTAR.
- CUSTOM.
- MQTT/AMQP/Azure/AWS en futuro.

LoopTransport sigue siendo transporte de referencia/test, pero el ejemplo ZON actual usado para params se ha centrado en MCAST/BCAST/UDPSTAR/USOXSTAR.

Regla:
- El transporte fisico solo mueve bytes.
- La serializacion y cifrado corresponden a infraestructura comun.
- Transportes no conocen tipos protobuf concretos.

### =====================================================================
BINARAFORMATO / BINARYFORMAT
### =====================================================================

ProtobuZig genera BinaraFormato:
- BF_PROTOBUF = 0
- BF_OMG_CDR = 1
- BF_ASN1_BER = 2
- BF_ASN1_DER = 3
- BF_BASE64 = 10
- BF_BINPB2TEKSTO_HEX = 11
- BF_BINPB2TEKSTO_DEC = 12

Config.proto define BinaryFormat:
- BF_PROTOBUF = 0
- BF_OMG_CDR = 1
- BF_ASN1_BER = 2
- BF_ASN1_DER = 3

Nota:
- Aunque tengan mismo backing integer, en Zig son tipos distintos.
- Usar helper explicito para convertir.
