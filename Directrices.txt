K6BUS - DIRECTRICES DE DESARROLLO Y DISEÑO
Actualizado: 2026-08-18

PRINCIPIO RECTOR
- Las aplicaciones intercambian mensajes.
- La topologia se define por configuracion.
- La infraestructura debe ser robusta, desacoplada y distribuible.
- Priorizar simplicidad, ownership claro y pruebas de round-trip frente a microoptimizaciones tempranas.

FILOSOFIA GENERAL
- La aplicacion define mensajes, publishers, subscribers y logica.
- La configuracion define infraestructura.
- No compartir objetos de aplicacion entre nodos.
- Todo intercambio entre nodos ocurre mediante mensajes.
- La logica real vive en Zig.
- APIs externas son fachadas.
- La API Zig segura generada por ProtobuZig es la frontera recomendada para construccion ergonomica de mensajes.
- El raw/impl generado debe seguir siendo una capa interna de datos, serializacion y deserializacion.

CONFIGURACION
- Config.proto es el contrato formal de K6Bus.
- AppConfig/DomainConfig completos son configuracion temporal de arranque.
- Domain no conserva el arbol completo de configuracion parseado.
- Domain conserva solo una configuracion runtime minima:
  - binary_format
  - dispatch_mode
  - dispatch_batch_time_ms
  - start_at_init
- app_cfg.deinit(allocator) debe ejecutarse tras init cuando ya no haya referencias prestadas.
- LoadTransports(dom_cfg) y CreateCrossConnections(dom_cfg) usan DomainConfig temporal durante init.
- Todo objeto creado desde configuracion debe copiar strings/slices que conserve tras createEx().
- Los wrappers *_api.zig generados desde Config.proto pueden usarse como API segura de construccion, validacion y pruebas, pero el runtime debe seguir controlando su ownership interno.

DOMAIN
- No usar singleton.
- Pueden coexistir multiples Domain.
- Domain debe crearse mediante create() -> *Domain o createEx() -> *Domain.
- No devolver Domain por valor.
- Objetos referenciados por hilos/callbacks deben tener direccion estable.
- create() usa configuracion sin overrides.
- createEx() permite overrides puntuales.
- init() centraliza la inicializacion interna.
- Domain.close() es cierre rapido.
- running=false debe establecerse al principio de close().
- close() no garantiza entrega completa.
- close() no debe bloquear indefinidamente.
- close() nunca debe producir leaks ni double-free.

QUEUEMGR
- Solo gestiona colas, mutex, condiciones, threads, batching y dispatch.
- No conoce canales, subscribers, transportes ni protobuf.
- Soporta IMMEDIATE y BATCH.
- Durante shutdown puede descartar mensajes pendientes liberandolos correctamente.

STREAMQUEUE
- StreamQueueUP filtra y distribuye hacia subscribers.
- StreamQueueDOWN distribuye hacia transportes y entrega local.
- No conoce tipos protobuf concretos.
- Trabaja sobre Msg y MsgList genericos.

SUBSCRIBER
- Un Subscriber por tipo de mensaje.
- Debe tener cola e hilo propios.
- El codigo de usuario nunca debe ejecutarse en hilos de infraestructura.
- Callbacks siempre desacoplados.
- Subscribers con QueueMgr deben alojarse en heap.

PUBLISHER
- Un Publisher por tipo.
- Publica mediante Domain.sendMsg().
- No conoce transportes ni subscribers.

TRANSPORT
- El transporte fisico solo mueve bytes.
- No conoce tipos protobuf concretos.
- No conoce logica de negocio.
- Codificacion RAW/BASE64 pertenece al transporte.
- Cifrado se define a nivel Domain y se ejecuta sobre bytes serializados.
- Los transportes que conserven strings/slices recibidos desde configuracion deben duplicarlos.

OWNERSHIP
- create/initDefault equivalen a constructor.
- deinit equivale a destructor.
- Cada objeto debe tener propietario claro.
- cloneMsg/cloneMsgSlice necesitan ruta clara de liberacion.
- enqueue transfiere ownership si tiene exito.
- Si enqueue falla, libera el propietario actual.
- No leaks en shutdown.
- No double-free.
- En la API segura generada:
  - getX() de scalar/enum/string/bytes devuelve valor o vista borrowed.
  - getXAt() de repeated scalar/string devuelve valor o vista borrowed.
  - getX() y getXAt() de message devuelven copia owned y el usuario debe llamar deinit().
  - setX()/appendX() de message hacen copia profunda.
  - oneof libera siempre la rama previa antes de activar una nueva.

PROTOBUZIG
- Independiente de K6Bus.
- Usa mecha como dependencia externa para parsing.
- Genera Zig raw/impl y API segura *_api.zig.
- initDefault() es mecanismo estandar de construccion.
- Debe mantenerse simetria initDefault()/deinit().
- oneof se representa como union(enum).
- oneof debe tener alternativa interna none: void para initDefault().
- oneof significa at-most-one, no exactly-one.
- oneof no tiene wire-format propio; cada alternativa se codifica como campo normal.
- Si al deserializar aparecen varias alternativas del mismo oneof, gana la ultima y debe liberarse la anterior.
- La deserializacion parte de initDefault() y aplica los campos recibidos; si un campo con default no aparece, conserva el default materializado por initDefault().
- Los optional con default se materializan en initDefault(); los optional sin default se inicializan a null.
- La serializacion binaria de optional debe escribir todo campo != null, aunque su valor sea igual al default.
- Los repeated deben preservar orden tras round-trip binario. Dado que EncodeBuffer escribe hacia atras/prepend, la serializacion de repeated se genera recorriendo el slice en orden inverso.
- BF_BASE64 usa buffer temporal decoded owned y debe liberarlo tras deserializar.

PROTOBUZIG - API SEGURA GENERADA
- kgenapi.zig genera *_api.zig junto al raw generado.
- kgapi_auks.zig contiene helpers de nombres y clasificacion de campos para la API.
- Cada wrapper publico tiene forma struct { impl: TipoImpl }.
- Los aliases TipoImpl desacoplan el wrapper de la fase raw actual y facilitan futura fase *_impl.
- cloneImpl(comptime T) usa seriigiAlBin(.BF_PROTOBUF) + deseriigiElBin(.BF_PROTOBUF) como copia profunda inicial.
- Cada wrapper genera clone() como copia owned.
- Cubierto en API segura:
  - required/optional/repeated scalar y enum.
  - required/optional/repeated string y bytes.
  - required/optional/repeated message.
  - oneof message, scalar, enum, string y bytes.
- Las ramas oneof siguen esta regla:
  - set clona/duplica primero.
  - clear libera la rama previa segun tipo.
  - has general y has por rama indican estado activo.
  - get de message devuelve copia owned.
  - get de string/bytes devuelve vista borrowed.

PROTOBUZIG - DEFAULTS STRING/BYTES
- Los defaults owned deben materializarse solo en initDefault().
- No conviene generar literales estaticos en campos que deinit() libera.
- Evitar que struct literals parciales puedan producir frees sobre literales estaticos.
- Pendiente revisar y endurecer la generacion de defaults explicitos para string/bytes.

BINARAFORMATO / BINARYFORMAT
- BinaraFormato generado por ProtobuZig y BinaryFormat de Config.proto pueden compartir valores numericos comunes.
- Zig los trata como tipos nominalmente distintos.
- Usar conversion explicita con @intFromEnum/std.meta.intToEnum.
- Recordar que BinaraFormato incluye representaciones auxiliares Base64/Hex/Dec.

BATCHING
- Batching global desde Domain.
- IMMEDIATE y BATCH.
- dispatch_batch_time_ms pertenece a configuracion runtime del Domain.
- Transparente para publishers/subscribers.

LOCKS
- Registry -> RwLock.
- Transportes -> RwLock.
- Colas internas -> Mutex.
- No ejecutar logica de usuario bajo lock.

CROSSCONNECTOR
- Intra-instancia.
- Conecta Transport <-> Transport.
- Domain crea topologia durante init usando configuracion temporal.
- Debe evitar bucles infinitos por mensajes propios en transportes tipo mcast/bcast.

ROBUSTEZ
- Priorizar robustez, aislamiento y simplicidad.
- No microoptimizar antes de medir.
- Recepcion siempre desacoplada mediante colas.
- Ante conflicto rendimiento/robustez, priorizar robustez.

WORKSPACE
- src/core contiene runtime K6Bus.
- src/generated contiene codigo generado por ProtobuZig, incluyendo raw y *_api.zig.
- tools/protobuzig puede ser enlace al binario de ProtobuZig.
- Cuidado: tras modificar ProtobuZig, recompilar y asegurar que K6Bus usa el binario correcto.
- Evitar directorios generated duplicados fuera de la ruta prevista para no validar ficheros equivocados.
